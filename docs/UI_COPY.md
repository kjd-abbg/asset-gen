# 사용자 화면 문구

제품의 고정 안내·버튼·오류·로딩·빈 화면과 그 스켈레톤에 적용한다. 사용자 입력, 저장된 생성물, 인용, 계약 원문은 구분한다. 특정 표현으로 AI 작성 여부를 판별하지 않는다.

## 편집 기준

- 제목은 기능이나 목적, 버튼은 누른 뒤 할 일을 말한다. 오류는 실패한 작업과 다음 행동을 알린다.
- 과장·의례적 칭찬·불필요한 대조·감정 추측·추상적 비유를 실제 기능·상태·행동으로 바꾼다.
- 대시로 설명을 덧붙이지 않는다. 필요하면 문장이나 문단으로 나눈다.
- ‘여정·가능성·온도’로 생성·저장·수정 작업을 대신 설명하지 않는다. 기능을 의인화하지 않는다.
- 근거 없는 시간·성과·학습 규모·품질 보장을 추가하지 않는다. 모르는 오류 원인을 추측하지 않는다.
- 쉬운 단어와 자연스러운 존대를 쓴다. 해요체 자체를 금지하지 않는다. 대상·조건을 생략해 짧게 만들지 않는다.
- 요금·권한·동의·삭제·환불 조건은 보존한다. 의미 있는 비교까지 단어만 보고 지우지 않는다.
- 변수 뒤에 조사를 고정하지 않는다("{이름}를"). 받침에 따라 고르는 헬퍼를 쓰고, 판별할 수 없는 영문은 "을(를)"로 쓴다(사례 D13).
- 삭제 문구는 실제 동작과 맞춘다. 복구 가능한 휴지통 이동(복구 기간 명시)과 영구 삭제를 나누고 "되돌릴 수 없습니다"는 영구 삭제에만 쓴다.
- 사용자에게 넘기는 산출물(PDF·문서·공개 페이지)에 작업 안내, 내부 메모, 빈 자리표시를 렌더하지 않는다. 빈 칸은 빼거나 "입력 필요"로 표시하고, 목차·"미리보기" 같은 라벨은 실제 내용과 일치시킨다.

## 문단 너비와 줄바꿈

줄바꿈이 어색하면 원문 개행과 브라우저 자동 줄바꿈을 먼저 구분한다. 문단과 부모의 실제 너비, width/max-width, 그리드 열, flex-basis, 패딩, white-space, word-break를 확인한다. 모든 줄바꿈을 같은 원인으로 단정하지 않는다.

결과 비교·폼·상태 안내는 해당 영역의 가용 너비를 기본으로 쓴다. 오른쪽 공간을 남기는 임의의 ch/px 상한으로 설명을 좁히지 않는다. 긴 글의 읽기 폭, 카드·사이드바, 의도한 제목 구성은 역할과 화면 검증에 근거해 제한할 수 있다. ch 값을 한글 글자 수로 간주하지 않는다.

줄 길이 기준은 이 절에서 정하며, 근거는 약하고 서로 다르다. 45~75자(Bringhurst)·66자 이상치는 세리프 인쇄 관행의 서술이고, 화면 연구는 긴 줄이 훑기는 빠르고 짧은 줄이 선호됐다(Ling & van Schaik 2006). 한글은 30자 미만으로 좁히지 않는 것까지가 약한 근거다(신종현 2003, 시험 최대 50cpl). WCAG 1.4.8(AAA)의 CJK 40자는 긴 글 본문(문서·도움말·기사)에만 참고 상한으로 쓸 수 있다. 상한을 둘 때는 em 단위로 폭을 정하고 렌더된 줄의 글자 수를 실측해 남긴다. `ch`·`ic`로 한글 글자 수를 추정하지 않는다.

한국어 줄바꿈 기본값은 전역 `word-break: keep-all; overflow-wrap: anywhere;`(KRDS 공통 CSS도 keep-all), 제목 `text-wrap: balance`, 본문 `text-wrap: pretty`로 둔다. balance는 주요 브라우저가 지원하고(Chromium 6줄·Firefox 10줄 이하에만 적용) pretty는 Firefox가 무시해도 안전하다. `word-break: auto-phrase`와 `line-break: strict`는 한국어 기본값으로 필요하지 않다(BudouX도 한국어는 keep-all을 권장).

화면의 줄 수만으로 문장을 쪼개거나 br·수동 개행을 넣지 않는다. 문단은 의미 단위로 나누고 일반 본문은 반응형 자동 줄바꿈을 사용한다. 좁은 화면에서 줄이 늘어나는 것은 정상이며 한 줄을 만들려고 nowrap·고정 최소 너비·글자 축소를 강제하지 않는다. 저장된 생성 설명과 사용자 원문은 레이아웃 수정 때문에 재작성하지 않는다.

복사하거나 대조해야 하는 값(코드, 토큰, 주소, DNS 값)은 nowrap·말줄임으로 자르지 않고 `overflow-wrap: anywhere`로 줄바꿈한다. 길이가 변하는 텍스트를 고정된 틀(카드·명함·썸네일)에 맞출 때는 틀 넓히기 → 줄바꿈 → 자간 → 하한이 있는 크기 축소 → 말줄임 순서로 시도하고 원문은 고치지 않으며, 가장 긴 실제 입력으로 렌더해 확인한다.

## 점검과 검사

페이지·상태·공통 문구의 원본을 찾아 목록을 만든다. 문자열 검색 후 사용자 노출 여부와 문맥을 검토한다. 반복 표현은 원본에서 고치고 스켈레톤에도 반영한다. 모바일 줄바꿈과 오류·로딩 상태는 [UI 검증](UI_VALIDATION.md) 절차를 따른다.

스택 어댑터는 사용자 노출 문자열을 `[{"source":"path:line","text":"문구"}]` JSON 배열로 추출할 수 있다. TS/JSX라면 AST를 사용해 주석·식별자·프롬프트와 템플릿 문장을 구분한다. 아래 검사는 추출된 문구의 명확한 금지 표현만 검사한다. 자동 추출기나 전체 문맥 판정기는 아니다.

```sh
python3 tool/check-ui-copy.py /tmp/ui-copy.json
```

프로젝트 어댑터를 만든 뒤 기존 test 또는 check에 연결한다. 아직 연결하지 않았다면 활성 센서라고 보고하지 않는다. 빈 입력·잘못된 형식·파일 누락은 exit2, 문구 위반은 exit1이다. source 위치만 출력해 고객 문구가 로그에 그대로 남지 않게 한다. 실제 고객 데이터는 추출하지 않는다. 새 프로젝트와 update에서 도구를 배치하지만 기존 Makefile을 자동 수정하지 않는다.

## 근거와 한계

- [국립국어원, 쉬운 공공언어 쓰기 길잡이](https://www.korean.go.kr/front/etcData/etcDataView.do?etc_seq=399&mn_id=208): 독자가 이해할 어휘와 정확하고 명료한 정보 제시.
- [NN/g, 웹 글쓰기 연구](https://www.nngroup.com/articles/concise-scannable-and-objective-how-to-write-for-the-web/): 간결하고 훑어보기 쉬운 객관적 문구를 연구에서 비교했다.
- [GOV.UK, Use clear language](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/writing-guidelines/clear-language/): 익숙한 단어, 구체적인 설명, 능동 표현, 짧은 문장.

영어 문장의 단어 수를 한국어에 그대로 강제하지 않는다. 대시 금지와 표현 목록은 제품 편집 선택이며 보편적인 AI 문장 판별법이 아니다. 센서 통과만으로 자연스러움·사실·법적 정확성을 보장하지 않는다.
