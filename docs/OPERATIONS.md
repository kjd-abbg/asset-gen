# 운영 기반: 배포·감시·로그·백업·장애 대응·비용

사용자가 쓰는 서비스(웹, 앱 백엔드, API)를 1인이 운영한다는 전제로 출시 전에 갖출 운영 기반에 적용. 운영 서버·영속 데이터가 없는 저장소(라이브러리, CLI, 정적 문서)는 해당하는 행만 적용.
키트는 관측성·트레이싱 도구 통합과 프로덕션 런타임 센서를 배치하지 않음([출처와 결정](SOURCES.md) "명시적으로 하지 않은 것"). 이 문서는 무엇을 갖추고 어떻게 확인할지만 정하며, 도구는 스택에서 고르고 `decisions.md`에 기록. `make check` 통과를 운영 기반이 갖춰졌다는 증거로 보고하지 말 것.
비밀값·보안 이벤트·레이트 리밋은 [보안](SECURITY.md), 로그·백업 속 개인정보와 유출 신고는 [개인정보·법적 고지](PRIVACY_LEGAL.md), 출시 기준과 제품 지표는 [기획](PRODUCT_PLANNING.md), 운영 빌드 화면 검증은 [UI 검증](UI_VALIDATION.md)을 따를 것.

## 출시 전 최소 운영 기반

| 항목 | 1인 기준 | 갖출 것 | 출시 전 확인 |
| --- | --- | --- | --- |
| 환경 분리 | 필수 | 개발 환경과 운영 환경의 설정·데이터·비밀값 분리 | 개발 설정으로 운영 DB에 연결되지 않음 |
| 재현 가능한 배포 | 필수 | 커밋 해시 기준 빌드, lockfile, 배포 기록 | 지금 운영 중인 커밋을 배포 기록에서 바로 찾음 |
| 되돌리기 | 필수 | 직전 버전 재배포 절차, 마이그레이션 되돌림 계획 | 롤백 리허설 1회 기록 |
| 외부 가용성 확인 | 필수 | 서비스 밖에서 주기적으로 호출하는 헬스체크 | 실패 주입 시 알림 도착 |
| 오류 알림 | 필수 | 처리되지 않은 예외·5xx 증가가 사람에게 도달 | 테스트 알림 수신 |
| 구조화 로그 | 필수 | 요청 id 포함, 보존 기간 지정 | 요청 id 하나로 한 요청의 로그를 모두 조회 |
| 백업·복구 | 영속 데이터가 있으면 필수 | RPO·RTO, 자동 백업, 다른 위치의 사본 | 별도 환경 복구 연습 1회 기록 |
| 비용 상한·알림 | 종량 과금이 있으면 필수 | 예산 알림, 유료 외부 API 호출 상한 | 알림 수신 경로 확인 |
| 런북 | 필수 | 아래 장애 대응 절차와 접속 위치를 담은 한 쪽 문서 | 사용자가 읽고 위치 확인 |
| staging | 권장 | 운영과 같은 구성, 운영 데이터 없음, 검색 비노출([SEO_GEO](SEO_GEO.md)) | 결제·마이그레이션·외부 연동이 있으면 필수로 올림 |
| feature flag | 권장 | 위험한 기능을 배포 없이 끄는 스위치 | 끄기 동작 확인 |
| SLO·error budget | 선택 | SLI 1~2개 | 측정값이 실제로 쌓임 |
| 상태 공지 채널 | 권장 | 상태 페이지, 앱 내 배너, 공지 계정 중 하나 | 게시 권한과 절차 확인 |

필수·권장 구분과 출시 전 확인 항목은 키트 규칙. 기획 문서의 출시 기준 "되돌리거나 끄는 방법"은 위 되돌리기·feature flag 행으로 충족 여부를 판단.

## 환경과 설정

- 1인 기준 최소 구성은 개발(로컬)과 운영. 미리보기 배포를 staging 대신 쓸 수 있으나 운영 DB·운영 비밀값을 연결하지 말 것(키트 규칙).
- 배포마다 달라지는 값(DB 주소, 외부 서비스 자격 증명, 도메인)은 모두 설정으로 보고 환경 변수로 주입(12-Factor III). 점검 질문: 지금 코드를 공개해도 자격 증명이 새지 않는가.
- 앱 시작 시 필수 환경 변수를 검사하고 빠지면 즉시 종료해 잘못된 설정으로 뜨지 않게 할 것(키트 규칙). 환경 변수 이름 목록은 `.env.example` 같은 형태로 저장소에 두고 값은 넣지 않음.
- DB·캐시·큐 같은 backing service는 모든 환경에서 같은 종류·버전을 사용(12-Factor X). 개발 SQLite, 운영 PostgreSQL처럼 다르면 운영에서만 나는 오류를 개발에서 재현하지 못함.
- 운영 데이터를 복사해 개발·테스트하지 말 것. 필요하면 합성 데이터를 쓰고, 운영 데이터 반출이 불가피하면 [개인정보·법적 고지](PRIVACY_LEGAL.md) 기준으로 사용자 결정을 받음.
- 프로세스는 언제든 멈추고 다시 뜰 수 있게 함: 빠른 시작, SIGTERM 수신 시 새 요청을 받지 않고 진행 중 작업을 끝낸 뒤 종료, 갑작스러운 중단에도 작업이 큐로 돌아가는 구조(12-Factor IX). 재배포·재시작 중 요청 유실 여부를 이 기준으로 확인.
- 비밀값 보관·교체는 [보안](SECURITY.md), 에이전트의 `.env` 접근 차단은 AGENTS §4 DENY와 `hooks/guard-secrets.sh`가 맡음.

## 배포와 롤백

- 같은 리비전을 다른 기계에서 빌드해도 같은 결과가 나와야 함(SRE Book 8장). lockfile을 커밋하고 빌드 도구 버전을 고정하며, 산출물과 응답 헤더 또는 헬스 응답에 커밋 해시를 남김.
- 배포 기록 항목: 시각(UTC), 커밋, 실행 주체(사람·에이전트·CI), 마이그레이션 포함 여부, 결과, 롤백 여부. 호스팅 플랫폼의 배포 이력으로 대신하면 그 위치를 런북에 적음.
- 되돌리는 방법은 배포 전에 정하고 확인: 직전 산출물 재배포, 플랫폼의 이전 배포 승격, 이전 이미지 태그 중 무엇을 쓰는지, 몇 분 안에 끝나는지 런북에 기록.
- DB 마이그레이션은 코드 롤백으로 되돌아가지 않는 경우가 많음. 호환되지 않는 스키마 변경은 expand → migrate → contract 순서로 나눔(Sato 2014, Parallel Change): 새 열·테이블 추가, 코드와 데이터 이전, 옛 구조 제거를 서로 다른 배포로. 한 배포에서 열 삭제·이름 변경을 하지 말고, 직전 버전 코드가 새 스키마에서 동작하는지 확인(키트 규칙).
- 데이터를 지우거나 덮어쓰는 마이그레이션은 직전 백업이 복구 가능한지 확인한 뒤 실행하고, 되돌릴 수 없다는 점을 배포 기록에 남김.
- feature flag로 기능 공개를 배포와 분리하면 다음 배포 전까지 문제 기능을 끌 수 있음(SRE Workbook 16장). 위험한 기능의 플래그는 기본값 꺼짐, 만든 날짜와 제거 예정일을 함께 기록(키트 규칙).
- canary는 변경의 부분적·시간 제한 배포와 평가(SRE Workbook 16장). 요청이 적은 1인 서비스는 표본이 작아 판단이 어려우므로 배포 직후 30분 동안 헬스체크·오류율·핵심 흐름을 직접 확인하는 것으로 대신함(키트 규칙). 한산한 시간 배포는 부하에서만 드러나는 성능 결함을 놓칠 수 있음(같은 장).
- 에이전트의 운영 배포·롤백·운영 DB 마이그레이션·운영 설정 변경은 AGENTS §4 ASK의 "되돌리기 어려운 행동" 자리에 넣을 것. 운영 DB 직접 쓰기는 DENY 후보. CI 배포 파이프라인과 필수 검사는 도입 저장소에서 연결(`decisions.md` 2026-09-14).
- DORA 지표(배포 빈도, 변경 리드타임, 변경 실패율, 실패 배포 복구 시간, 배포 rework rate)는 배포 기록에서 계산 가능. 1인 서비스는 변경 실패율과 복구 시간만 월 1회 보면 충분하며(키트 규칙), 지표를 목표치로 삼거나 다른 서비스와 비교하지 말 것(DORA).

## 감시와 알림

| 신호 (SRE Book 6장) | 정의 | 1인 서비스에서 볼 것 |
| --- | --- | --- |
| latency | 요청 처리 시간. 성공·실패 요청을 구분 | 주요 엔드포인트의 p95. 평균은 느린 꼬리를 가림(SRE Book 4장) |
| traffic | 시스템에 걸리는 수요 | 분당 요청 수, 평소 대비 급증(비용 폭주와 연결) |
| errors | 명시적(5xx)·암묵적(200이지만 잘못된 내용)·정책상 실패 비율 | 5xx 비율, 합성 검사로 잡는 잘못된 응답 |
| saturation | 가장 제약된 자원이 찬 정도 | DB 연결 수, 디스크, 메모리, 무료 한도·쿼터 사용률 |

- 사람을 부르는 알림은 증상(사용자에게 보이는 고장)에 걸고 원인 지표(CPU 등)는 조사용 화면에 둠. 모든 알림은 행동할 수 있어야 하고, 기계적으로 대응하는 알림은 자동화 대상(SRE Book 6장).
- 외부 헬스체크는 블랙박스 감시(사용자처럼 밖에서 보는 동작 검사, SRE Book 6장). 서비스와 다른 업체·지역에서 1~5분 간격으로 호출하고 2회 연속 실패 시 알림(키트 기본값). 헬스 엔드포인트는 프로세스 생존만 보는 것과 DB 등 핵심 의존성까지 보는 것을 구분해 정하고, 로그인 뒤 핵심 동작 같은 흐름 검사를 권장.
- 수신 경로: 1인이 실제로 보는 채널 1개(휴대폰 푸시·SMS)와 대체 채널 1개(이메일). 감시 도구가 서비스와 같은 플랫폼에만 있으면 함께 멈추므로 외부 헬스체크 하나는 분리(키트 규칙).
- 소음 관리: 알림을 정밀도·재현율·감지 시간·해제 시간으로 평가(SRE Workbook 5장). 행동 없이 닫은 알림이 한 주에 반복되면 임계값을 조정하거나 삭제하고 그 결정을 기록(키트 규칙).
- SLO는 선택. 쓰면 SLI는 가용성·지연 중 1~2개, 목표 100%는 금지(SRE Book 3장), 현재 성능을 그대로 목표로 삼지 말 것(SRE Book 4장). error budget이 바닥나면 기능 배포를 멈추고 안정화를 우선.
- burn-rate 알림의 시작점은 99.9% SLO 기준 1시간 창 14.4배(예산 2%)와 6시간 창 6배(5%)는 호출, 3일 창 1배(10%)는 티켓(SRE Workbook 5장 표 5-8). 요청이 적으면 실패 몇 건으로 오탐이 나므로 합성 트래픽을 만들거나 영향에 맞춰 목표를 낮춤(같은 장).

## 로그

- 각 프로세스는 로그를 stdout 이벤트 스트림으로 쓰고 수집·보관은 실행 환경에 맡김(12-Factor XI).
- 일정한 스키마를 가진 구조화 로그(JSON 등)로 기록(OpenTelemetry Logs). 기본 필드: `timestamp`(UTC, ISO 8601), `level`, 이벤트 종류와 메시지, `request_id`, 서비스 이름과 버전(커밋), 내부 사용자 id(인증된 경우), 경로, 상태 코드, 소요 시간. OWASP의 when·where·who·what 항목과 대응.
- 요청 id는 진입점에서 만들거나 받은 값을 응답 헤더, 모든 하위 로그, 외부 호출에 전달. 트레이싱을 도입하면 trace id·span id가 이 역할을 맡지만(OpenTelemetry) 도입 여부는 스택에서 정함.
- 레벨 기준(키트 규칙): ERROR는 사람이 볼 일(알림 후보), WARN은 자동 복구된 이상, INFO는 요청·배포·작업 단위 기록, DEBUG는 운영에서 기본 꺼짐. 서버 시간은 동기화해 둘 것(OWASP).
- 넣지 말 것: 비밀번호, 세션 id, 토큰, 연결 문자열, 암호화 키, 결제 정보(OWASP Logging 목록, 세부는 [보안](SECURITY.md)), 개인정보([개인정보·법적 고지](PRIVACY_LEGAL.md)). 보안 이벤트로 남길 항목도 보안 문서를 따름.
- 보존 기간은 정한 기간 전에 지우지 않고 그 뒤로 남기지 않음(OWASP). 기간 자체는 장애 조사에 필요한 기간과 개인정보 보존 원칙을 함께 보고 정해 `decisions.md`에 기록. 플랫폼 기본 보존이 조사 기간보다 짧으면 외부로 내보낼지 결정.

## 백업과 복구

- RPO는 장애 뒤 데이터를 되살려야 하는 시점, RTO는 시스템이 복구 단계에 머물러도 업무에 지장이 없는 시간(NIST SP 800-34). 두 값을 사용자와 정해 `decisions.md`에 적고, 백업 주기는 RPO 이하로.
- 백업은 자동으로 정기 실행(CISA). 대상: DB, 사용자 업로드 파일, 환경 변수 이름 목록과 인프라 정의(비밀값 원문 제외). 코드는 git이 보관.
- 3-2-1: 사본 3개, 저장 매체 2종, 1개는 다른 장소(CISA). 클라우드 1인 서비스의 해석(키트 규칙): 운영 DB, 같은 업체의 자동 스냅샷·PITR, 다른 계정이나 다른 업체 저장소의 사본. 다른 장소 사본의 자격 증명은 운영과 분리하고 암호화(CISA의 암호화·오프라인 사본 권고).
- 백업은 정기적으로 시험해 오류 없이 꺼낼 수 있는지 확인(NIST SP 800-34 3.4.2). 전체·부분 복구와 최소 7일 전 시점으로 되돌리기를 연습(CISA).
- 복구 연습 주기(키트 규칙): 출시 전 1회, 이후 분기 1회, 스키마나 백업 방식이 크게 바뀐 뒤 1회. NIST 정책 예시는 연 1회 시험이므로 분기 주기는 1인 서비스의 변경 속도를 반영한 키트 값.
- 복구는 운영을 덮어쓰지 말고 별도 환경에서 실행. 기록 항목: 날짜, 사용한 백업 시점, 걸린 시간(RTO 대비), 잃은 데이터 범위(RPO 대비), 행 수·최근 레코드 확인 결과, 막힌 단계.
- 백업 속 개인정보의 보존·파기는 [개인정보·법적 고지](PRIVACY_LEGAL.md)를 따름.

## 장애 대응

| 단계 | 1인 런북에서 할 일 | 기록 |
| --- | --- | --- |
| 감지 | 알림·사용자 문의로 인지. 사용자에게 보이거나, 1시간 집중 분석에도 풀리지 않거나, 외부 업체 도움이 필요하면 장애로 선언(SRE Book 14장 기준을 1인용으로 조정) | 인지 시각, 경로 |
| 완화 | 원인 규명보다 영향 축소를 먼저: 롤백, 플래그 끄기, 점검 모드, 문제 기능 차단 | 조치와 시각 |
| 공지 | 영향 범위, 인지 시각, 다음 안내 시각을 상태 공지 채널에 게시. 확인하지 않은 원인은 쓰지 않음([제품 문구](UI_COPY.md)) | 게시 시각 |
| 복구 | 헬스체크·핵심 흐름·데이터 정합성 확인 뒤 종료 공지 | 종료 시각 |
| 회고 | 비난 없는 회고: 영향, 조치, 원인, 후속 작업(SRE Book 15장) | 회고 문서, 후속 작업 |

- 장애 중에는 시간순 메모 하나를 계속 갱신(SRE Book 14장의 living incident document를 1인용으로 축소). 회고 대상: 사용자에게 보인 중단·저하, 데이터 손실, 롤백 같은 수동 개입, 사용자가 먼저 알려 준 경우(감시 실패, SRE Book 15장).
- 보안 사고 대응의 구성은 NIST SP 800-61r3(CSF 2.0의 Detect·Respond·Recover)를 참고하고 구체 절차는 [보안](SECURITY.md)을 따름. 개인정보 유출이면 [개인정보·법적 고지](PRIVACY_LEGAL.md)의 통지·신고 절차로 넘어감(개인정보 보호법 시행령 제39조·제40조, 알게 된 때부터 72시간 기준).
- 사고 조사에 필요한 로그·백업은 보존 기간 회전으로 지워지기 전에 사본을 남김(키트 규칙).
- 에이전트는 로그 분석, 완화 절차 제안, 공지·회고 초안을 맡음. 장애 중에도 운영 변경은 AGENTS §4 ASK를 거침.

## 비용

- 클라우드 업체의 예산 알림을 켬(예: AWS Budgets, Google Cloud 예산, Vercel Spend Management). 예산만 설정해서는 사용이 멈추지 않는 업체가 있으니 확인할 것: Google Cloud 알림 전용 예산은 사용을 막지 않고, Vercel은 별도 일시정지 옵션을 켜야 함.
- 알림은 지연됨: AWS Budgets 데이터는 하루 최대 3회 갱신, Vercel은 몇 분 간격 확인. 감당할 수 있는 최대 금액보다 낮게 설정하고 실제 지출과 예측 지출 알림을 함께 사용. 업체 기본 임계값 예는 Google Cloud 50·90·100%, Vercel 50·75·100%.
- 자동 차단(예: Vercel 운영 배포 일시정지, 방문자에게 503)은 비용과 서비스 중단 사이의 선택이므로 사용자가 정하고 `decisions.md`에 기록.
- 사용량 폭주 차단: 유료 외부 API(LLM 등)의 일일 호출·토큰 상한을 앱 안에 두고, 재시도 횟수 상한, 업로드 크기 상한을 설정. 요청 단위 레이트 리밋은 [보안](SECURITY.md).
- 무료 한도에 닿을 때 차단되는지 과금으로 넘어가는지 업체 문서로 확인해 런북에 적음. 비용이 드는 외부 서비스 추가는 사용자 결정([기획](PRODUCT_PLANNING.md) 에이전트 운용 규칙).

## 검증 방법

| 확인 | 방법 | 통과 기준 | 시점 |
| --- | --- | --- | --- |
| 롤백 리허설 | staging·미리보기에서 새 버전 배포 후 직전 버전으로 되돌림 | 런북의 시간 안에 이전 커밋 해시가 응답 | 출시 전, 배포 방식 변경 시 |
| 마이그레이션 호환 | 새 스키마에 직전 버전 코드를 붙여 핵심 흐름 실행 | 오류 없음 | 스키마 변경마다 |
| 복구 연습 | 별도 환경에 백업 복원 | RTO 안에 끝나고 손실이 RPO 이내 | 출시 전, 분기 |
| 알림 테스트 | 테스트 오류를 일으키거나 도구의 테스트 발송 | 주 채널·대체 채널 모두 5분 안에 수신(키트 기본값) | 출시 전, 경로 변경 시 |
| 헬스체크 실패 주입 | 헬스 엔드포인트를 실패로 바꾸거나 의존성 연결을 끊음 | 알림 도착, 복구 뒤 해제 | 출시 전 |
| 설정 검사 | 필수 환경 변수 하나를 빼고 실행 | 시작 실패와 누락 이름 출력 | 출시 전 |

오용 주의:
- SRE 책은 Google 규모의 팀 운영 기준이라 사고 역할 분리, canary 크기, burn-rate 표를 1인 저트래픽 서비스에 그대로 옮기지 말 것. 표 5-8은 99.9% SLO 기준 시작점.

- NIST SP 800-34는 미국 연방 정보시스템 대상이고 CISA 3-2-1은 소기업 일반 권고라, 클라우드 사본 구성은 키트의 해석. 업체의 임계값·갱신 주기·차단 기능은 예고 없이 바뀌므로 설정 시점에 다시 확인.
