# 화면 작업 시작점

UI가 있는 프로젝트에서 화면·컴포넌트·페이지를 만들 때 가장 먼저 읽는 문서. 기본값, 반드시 지킬 것, 절차만 담음.
상세 기준은 아래 표의 해당 절만 골라 읽고, 근거와 한계가 필요할 때만 [디자인 참고자료](DESIGN_LIBRARY.md)를 연다.
사용자가 준 브랜드 자료·기존 디자인 시스템, 루트 `DESIGN.md`, 프로젝트 `decisions.md`가 이 문서의 기본값보다 우선.

## 기본값

프로젝트가 정하지 않았을 때 쓰는 값. 바꾸면 `decisions.md`에 이유를 남김. 값의 근거와 대안은 오른쪽 문서.

| 항목 | 기본값 | 담당 |
| --- | --- | --- |
| 글꼴 | Pretendard(공공은 Pretendard GOV) 한 가족. 영문 위주 브랜드면 라틴 글꼴 하나를 제목에 추가. 고른 이유 한 줄 기록 | DESIGN_TOKENS 타이포그래피 |
| 본문 크기·줄간격 | 1rem, 줄간격 1.5~1.7. 장문 위주·고령 대상은 더 큰 본문을 먼저 검토 | DESIGN_TOKENS, VISUAL_DESIGN 읽기 |
| 제목 | 인접 단계 비율 1.2~1.5, 줄간격 1.2~1.3, 히어로는 별도 display 단계 | DESIGN_TOKENS |
| 굵기 | 400·700, 필요하면 중간 하나 | DESIGN_TOKENS |
| 자간 | 본문·한글 제목 0. KRDS는 큰 제목에 +1px, 일부 국내 시스템은 큰 제목에 음수 자간을 씀. 바꾸면 기록 | DESIGN_TOKENS |

| 간격 | 4 단위 스케일(0·4·8·12·16·20·24·32·40·48·64·80·96), 그룹 안 < 그룹 사이 | DESIGN_TOKENS |

## 반드시 지킬 것

1. `spec/DESIGN-BRIEF.md`와 디자인 시스템(루트 `DESIGN.md`) 없이 화면을 그리지 않는다. 시스템은 getdesign.md에서 고르거나 섞어 정한다(DESIGN_SYSTEM). 사용자가 서두르면 빈 칸을 "가정:"으로 채워 확인받는다.
2. 색·크기·간격은 `DESIGN.md`에서 생성한 토큰만 쓴다. 값을 바꿀 때는 `DESIGN.md`를 고친다. 연결돼 있으면 `make design-md`와 `make design-literals`가 통과해야 한다.
3. 한 화면의 주 행동은 하나만 가장 두드러지고, 호버 전 기본 상태에서도 보인다.
4. 화면마다 빈·로딩·오류·성공·권한 없음 상태를 만든다.
5. 텍스트 대비 4.5:1, 컨트롤·포커스 표시 3:1, 모든 기능 키보드 조작, 포인터 대상 24px 이상.
6. 320px 폭과 200% 확대에서 가로 스크롤·잘림이 없다.
7. 첫 화면 상단에서 무엇을 하는 곳인지와 주 행동이 보인다. 100vh 히어로로 다음 내용을 가리지 않는다.
8. 데스크톱 주 메뉴를 햄버거에 숨기지 않고 현재 위치를 표시한다.
9. 링크·버튼 문구는 누른 뒤 일어날 일을 말한다("더 보기" 단독 금지).
10. 장식용 스톡 인물 사진과 자동 회전 캐러셀을 쓰지 않는다.
11. 가장 긴·가장 짧은 실제 콘텐츠로 확인한다. lorem ipsum으로 끝내지 않는다.
12. 스켈레톤은 정적이고 실제 화면과 같은 구조다.
13. 레이아웃 속성 전환과 `transition: all`을 쓰지 않는다. reduced motion에서는 JS 애니메이션·자동 재생까지 멈춘다.
14. 표의 숫자 열은 오른쪽 정렬과 `tabular-nums`. 양 비교 차트는 위치·길이로 그리고 파이·게이지를 쓰지 않는다.
15. 다크 패턴을 만들지 않는다(UX_DESIGN 정직한 설계).
16. DESIGN_REVIEW의 범용 AI 화면 징후가 브리프 근거 없이 나오면 고친다.
17. 렌더 리뷰는 구현에 참여하지 않은 리뷰어가 한다(아래 절차 4).
18. 사람이 해야 하는 확인을 에이전트 결과로 대신 보고하지 않는다.

## 절차

1. 브리프: `spec/DESIGN-BRIEF.md`를 채우고 결정자 칸은 사용자 확인을 받는다.
2. 디자인 시스템: getdesign.md에서 브리프에 맞는 시스템을 고르거나 섞어 루트 `DESIGN.md`로 확정하고, 강조색 후보는 견본으로 비교해 사용자가 고른다(견본은 색 비교용이라고 알린다). 토큰을 생성해 스택에 연결한다(DESIGN_SYSTEM, DESIGN_TOKENS 스택 연결 절).
3. 구현: 화면마다 주 행동·상태·실제 콘텐츠를 갖춰 만들고 `make check`.
4. 독립 렌더 리뷰: 320·360·768·1024·1280px와 테마별 스크린샷을 찍고, 구현 맥락이 없는 리뷰어(새 서브에이전트)에게 스크린샷·브리프·리뷰표만 주어 판정받는다. 절차는 DESIGN_REVIEW 독립 리뷰 절.
5. 고치기: 위반을 고치거나 남길 이유를 `decisions.md`에 적는다.
6. 사람 확인과 인계: 아래 표의 미실행 항목을 `HANDOFF.md`에 남긴다.

## 사람이 해야 하는 일

에이전트가 할 수 없거나 해도 근거가 되지 않는 것. 하지 않았으면 "미실행"으로 보고한다.

| 일 | 왜 사람인가 |
| --- | --- |
| 브랜드 성격·밀도·다크 제공 결정, 디자인 시스템 출발점·강조색 선택 | 결정자의 선택 |
| 첫인상 확인(5초 테스트 등)과 시안 선호 비교 | 사용자 반응이 필요 |
| 주요 과업 사용성 확인 | 과업 성공 여부는 사람이 해 봐야 앎 |
| 스크린리더·실기기 확인 | headless 접근성 트리는 스크린리더가 아님 |
| 카드 소팅·트리 테스트 | 참가자가 필요 |
| 상표·법적 판정 | 전문가 영역 |

## 끝낼 때 보고

센서 결과(`make check`), 리뷰 스크린샷 경로와 리뷰표, 고치지 않은 위반과 이유, 미실행 항목을 함께 보고한다. 센서 통과와 에이전트 리뷰를 사용자 테스트 결과로 표현하지 않는다.
