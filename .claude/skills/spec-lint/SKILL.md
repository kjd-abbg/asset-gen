# 스펙 슬롯 검사

기획 문서가 **형식적으로 완결됐는지**만 본다. 내용의 타당성은
`implementability-review`가 본다. 둘을 섞지 않는다.

## 검사 대상과 필수 슬롯

| 문서 | 비면 실패인 슬롯 |
| --- | --- |
| `spec/PRODUCT-BRIEF.md` | 누구의 어떤 문제 / 가장 위험한 가설과 확인 방법 / 기간 / **하지 않을 것** / 출시 기준 |
| `spec/DESIGN-BRIEF.md` | 누가 어떤 상황에서 보나(화면 범위·지원 언어 포함) / 브랜드 성격 표 / **업종 관례 조사 3곳 이상(캡처 경로 포함)** / 레퍼런스 3개 이상(가져올 요소 포함) / 기초값(디자인 시스템 출발점 포함)과 **보유 자료** / **시각 No-gos**. 6번 밀도 칸이 숫자가 아니면 지적 |
| `spec/PRD-*.md` | 문제 정의 / 대상 사용자 / 성공 지표 / **비목표** / **엣지 케이스** / 수용 기준 |
| `spec/SCREENS.md` | 각 행의 **빈 상태**, **에러 상태**, 필요한 권한 |
| `spec/STATE-TRANSITIONS.md` | 최종 상태, **금지된 전이** |
| `spec/PERMISSIONS.md` | 역할 표, 리소스×동작 매트릭스, **필드 수준 제약** |
| `spec/DATA-MODEL.md` | 각 엔티티의 **불변식**, 삭제 정책 |
| `spec/GOLDEN-SCENARIOS.md` | 시나리오 1개 이상, 각 성공 판정 |

## 특히 엄격하게 볼 것

**비목표**와 **엣지 케이스**. 이 둘은 에이전트가 가장 성의 없이 채우는 칸이고,
비었을 때 대가가 가장 크다.

- **비목표가 비면** 범위가 무한해진다. 에이전트는 인접한 것을 전부 만들어도
  된다고 해석한다.
- **엣지 케이스가 비면** 해피패스만 구현된다. 그리고 그 구현은 테스트를 통과한다.

다음은 **채운 것으로 치지 않는다**: `<<<`가 남아 있는 것, "없음"만 있고 왜 없는지
없는 것, "추후 정의", "TBD", "협의 필요", 항목이 1개뿐인 엣지 케이스 표,
브리프 3번 표에서 결과 칸이 빈 행, 디자인 브리프 4번에서 "가져올 요소"가 "깔끔함"·"세련됨" 같은 형용사뿐인 행, 항목이 1개 이하인 디자인 브리프 7번, 항목이 1개 이하인 브리프 6번, 브리프 6번 항목이 빠진 PRD 비목표.

## 출력

```
[sensor:spec-lint] FAIL (3 issues)
  1. spec/PRD-알림.md:28 — 비목표 칸이 비어 있다 — FIX: 이번에 안 하는 것을 최소 2개, 왜 빼는지와 함께 적는다
  2. spec/PERMISSIONS.md — 필드 수준 제약 표가 없다 — FIX: 민감 필드와 마스킹 규칙을 적는다
  3. spec/SCREENS.md:11 — '목록' 화면의 에러 상태가 비어 있다 — FIX: 조회 실패 시 무엇을 보여줄지 적는다
```

지적이 없으면 `[sensor:spec-lint] PASS`.
