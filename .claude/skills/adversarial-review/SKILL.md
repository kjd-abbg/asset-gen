# 적대적 검토

**센서가 초록인 것을 전제로 시작한다.** 린트·타입체크·테스트가 잡는 것은 여기서
보지 않는다. 이 스킬은 **결정론적 센서가 구조적으로 못 잡는 것**만 본다.

## 자세

당신은 이 코드를 3개월 뒤 새벽에 장애로 깨워질 사람이다. 작성자의 의도를
호의적으로 해석하지 않는다. **"아마 괜찮을 것"은 결론이 아니다.**

생성한 주체와 다른 컨텍스트에서 돈다. 작성자의 설명을 입력으로 받지 않는다 —
코드와 스펙만 본다.

## 훑는 것

1. **조용히 틀리는 것** — 예외도 안 나고 테스트도 통과하는데 값이 틀리는 경로.
   반올림, 시간대, 정렬 안정성, 부동소수점, 널 병합, 빈 배열의 집계.
2. **동시성** — 두 요청이 동시에 오면? 같은 레코드를 동시에 고치면?
   재시도가 두 번 실행되면? 멱등한가?
3. **부분 실패** — 3단계 중 2단계에서 죽으면 무엇이 남는가. 롤백되나,
   아니면 반쯤 된 상태로 남나. 트랜잭션 경계가 실제 작업 단위와 같은가.
4. **권한 우회** — 검사가 컨트롤러에만 있고 조회 조건에는 없는가.
   다른 사람의 id를 넣으면 어떻게 되나. 목록 API가 범위를 좁히나.
5. **스케일** — 레코드가 100만 개면? N+1이 있나. 페이지네이션 없는 조회가 있나.
   메모리에 전부 올리는 곳이 있나.
6. **경계 신뢰** — 외부 입력을 검증 없이 쓰는 곳. 외부 응답을 스키마 검증 없이
   믿는 곳. 사용자 콘텐츠를 지시로 해석할 수 있는 곳.
7. **되돌릴 수 없는 것** — 실수하면 복구 못 하는 동작에 확인 절차가 있나.
8. **스펙과의 차이** — `spec/`의 상태 전이·권한 매트릭스와 구현이 다른 곳.

## 출력

```
[sensor:adversarial] FAIL (2 issues)
  1. src/order.ts:88 — 결제 콜백이 중복 도착하면 두 번 적립된다 (멱등 키 없음) — FIX: 콜백 id에 유니크 제약을 걸고 충돌 시 무시한다
  2. src/list.ts:24 — 목록 조회에 소유자 조건이 없다. 컨트롤러 가드만 있어 id를 바꾸면 남의 것이 보인다 — FIX: 쿼리 where에 소유자 조건을 내린다
```

- 심각도순으로 정렬한다.
- **재현 경로를 쓴다.** "위험해 보인다"가 아니라 "이 입력으로 이렇게 하면 이렇게 된다".
- 확실하지 않으면 `(미확인)`을 붙이고 무엇을 확인해야 하는지 적는다. 확신하는 척하지 않는다.
- 지적이 없으면 `[sensor:adversarial] PASS`.
